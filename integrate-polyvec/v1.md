# integrate-polyvec — v1

> **Prompt version: v1** (2026-10-15). Targets Polyvec `main` as of Phase 8.
> A newer prompt version supersedes this one; if a behavior changed, use
> the newer one. This file is mirrored in the docs site
> (AI integration prompt page) — same content, same version.
>
> Honesty rule, read first: **generated code is not a result.** This
> integration is complete only after a REAL query runs against a REAL
> `polyvec-server` process and returns verified evidence. A run that
> stops at "the code looks right" is a failure, not a shortcut.

## Goal

Integrate Polyvec (a Rust vector database over HTTP) into the target
project so the project can store documents and retrieve them by text
query, with evidence that it actually works.

## Prerequisites you must confirm before starting

- A machine (or container) where you can build/run Rust OR where a
  prebuilt `polyvec-server` binary can run. If you cannot run the server,
  stop and say so — do not fake it.
- Python 3.8+ (for the verification scripts) or equivalent HTTP tooling.
- Network access to crates.io only matters if building from source; the
  server itself needs no network at runtime (except a `remote` embedding
  provider you configure).

## Step 1 — Inspect the target project

1. Read the target project's README/stack: language, framework, runtime,
   how secrets are managed (env files, vault, CI secrets).
2. Decide where Polyvec fits: as a sidecar process the app talks to over
   HTTP (`127.0.0.1:8080` default), never as a library (there is no
   client SDK — HTTP is the only supported interface).
3. Note the constraint: the server binds **localhost only by default**.
   Non-loopback binds need `POLYVEC_ALLOW_NONLOCAL_BIND=1` **and** you
   must then set `POLYVEC_API_KEY` (see Step 2).

State these findings explicitly before continuing.

## Step 2 — Choose an integration pattern

Pick exactly one, and say why. Do not mix patterns in one collection:

| Pattern | When to use | What it needs |
| ------- | ----------- | ------------- |
| **A. Ingest pipeline + remote provider** | Real documents (HTML/Markdown/text/CSV) that must be embedded by Polyvec | `POLYVEC_EMBEDDING_PROVIDER=remote` + base URL + model + dimension + API key |
| **B. Ingest pipeline + supplied vectors** | You embed text in your own code (your own model, LangChain, etc.) | Vectors with 1:1 chunk correspondence; no provider needed |
| **C. Raw vectors + lexical query** | Documents stored with client-side ids; term search only | No provider needed for `lexical` mode; embedding side unused |
| **D. Ingest pipeline + stub provider** | **Local development / tests only.** The stub is a deterministic hash, not an embedding model | `POLYVEC_EMBEDDING_PROVIDER=stub`; retrieval-quality claims are invalid |

Never claim semantic-search quality from pattern D. Never expose an
embedding API key in code, logs, or committed files — env vars only
(`POLYVEC_EMBEDDING_API_KEY`).

## Step 3 — Configure the endpoint and secrets

1. Start (or point at) `polyvec-server`. Minimal local config:

   ```bash
   POLYVEC_BIND=127.0.0.1:8080 \
   POLYVEC_DATA_DIR=./polyvec-data \
   POLYVEC_EMBEDDING_PROVIDER=stub \
   POLYVEC_STUB_DIMENSION=64 \
   polyvec-server
   ```

2. Confirm `GET /healthz` returns `{"status":"ok",...}` and
   `GET /readyz` returns `{"status":"ready"}` before touching any `/v1`
   route.
3. If the server is reachable beyond localhost: set `POLYVEC_API_KEY` to a
   long random secret, require `Authorization: Bearer <key>` on every
   `/v1` call, and verify a wrong key gets `401`. Record that you did.

Secrets live in env vars / the target project's secret manager. They
never go into the test script, the repo, or this report's command logs.

## Step 4 — Create a collection and ingest a test document

1. Create a collection. `dimension` must match your embedding dimension
   (pattern B/D) and `metric` is `"l2"` or `"cosine"`:

   ```bash
   curl -X POST 127.0.0.1:8080/v1/collections \
     -H 'content-type: application/json' \
     -d '{"id":"<slug>","dimension":64,"metric":"cosine"}'
   # expect 201
   ```

2. Ingest one real document from the target project's domain (not
   `lorem ipsum`) via `POST /v1/collections/{id}/ingest` (patterns A/B/D)
   or `PUT /v1/collections/{id}/documents` (pattern C).
3. Poll `GET /v1/jobs/{job_id}` until the job is `done`. If it is
   `failed`, read the job's `error` object, fix the cause, and resubmit —
   do not proceed on a failed job.
4. Record: collection id, document id, job id, chunk count, and the
   exact `curl` commands you used.

## Step 5 — Run a REAL query and verify the evidence

This is the gate. All of it must happen against the running server:

1. Query with text from the ingested document, in a mode your pattern
   supports (`vector` needs a provider; `lexical` never does):

   ```bash
   curl -X POST 127.0.0.1:8080/v1/collections/<id>/query \
     -H 'content-type: application/json' \
     -d '{"text":"<a phrase from your document>","k":5,"mode":"lexical"}'
   ```

2. Verify in the response — by reading the actual JSON, not by assuming:
   - `hits` is non-empty and rank 1 is your document;
   - the hit carries `text` (a snippet of your document), `source`, and
     the document `metadata` you supplied;
   - `score_kind` matches the mode you asked for (`lexical` → `bm25`,
     `vector` → `distance`, `hybrid` → `rrf`).

3. Negative check: query with a term that appears nowhere in the
   document and confirm you do **not** get it back at rank 1 with
   fabricated-looking evidence (empty hits or unrelated hits are the
   honest answer — report what you saw).

If any verification fails, the integration is not done. Fix and re-run.

## Step 6 — Add application error handling and tests

In the target project, wrap every Polyvec call so that:

- connection failures and timeouts surface as the project's own error
  type (never a bare stack trace to the user);
- `429` (rate limit / job-queue backpressure) is retried with the
  `Retry-After` header honored, bounded (no infinite retry);
- `401`/`404`/`501` are surfaced, not swallowed — `501` means "no
  embedding provider configured", which is a deployment bug, not a
  runtime one.

Add at least one automated test that boots a real server (or connects to
a test instance), ingests a document, queries, and asserts the evidence
fields from Step 5. A test that only mocks the HTTP layer does not
count toward this prompt's verification.

## Step 7 — Report

Write the integration report with these sections:

1. **Changes** — files created/modified, integration pattern chosen and
   why, config values (never the secrets themselves).
2. **Verification commands** — every command you ran (server start,
   collection create, ingest, job poll, queries, negative check, test
   run) and the key output of each (status codes, job states, hit
   evidence). Paste, don't summarize.
3. **Unverified assumptions** — everything you did not check (e.g.
   "remote provider path not exercised — no API key available",
   "restart durability not re-verified in this run"). Be explicit.
4. **Known limits that apply** — the ones from the docs that touch this
   integration (stub provider mechanics-only, single-process rate
   limiter, `kill -9` over HTTP untested).

The integration is done when Steps 1–6 are executed for real and the
report above exists. Anything less is a draft — label it as such.
